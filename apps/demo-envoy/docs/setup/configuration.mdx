# Configuration

<Terminology title="Protocol translator and relay engine between systems" to="/docs/terminology#envoy">Envoy</Terminology> is configured through a `.grain` <Terminology title="Config file declaring every relay Envoy runs" to="/docs/terminology#relay-manifest-grain">relay manifest</Terminology>. The <Terminology title="Config file declaring every relay Envoy runs" to="/docs/terminology#relay-manifest-grain">manifest</Terminology> declares every <Terminology title="Single declared pipeline from a source to destinations" to="/docs/terminology#relay">relay</Terminology> — what it listens for, how it transforms the payload, where it delivers, and what happens when delivery fails.

## Relay Manifest Structure

A <Terminology title="Config file declaring every relay Envoy runs" to="/docs/terminology#relay-manifest-grain">relay manifest</Terminology> contains one or more `relay` blocks. Each block defines a complete pipeline from source to destination.

```text title="relay.grain"
relay "glassboard-to-canary" {
  source      = "glassboard"
  cipher      = "hmac-sha256"
  destination = "canary://infra-alerts"

  transform {
    title    = "[{{ severity }}] {{ alertname }}"
    body     = "{{ instance }} — {{ message }}"
    priority = severity_to_priority(severity)
    tags     = ["{{ severity_emoji }}"]
  }

  retry {
    strategy = "exponential"
    max      = 5
    backoff  = "1s, 5s, 30s, 2m, 10m"
  }
}

relay "threadbare-to-canary" {
  source      = "threadbare"
  cipher      = "hmac-sha256"
  destination = "canary://ci-builds"

  transform {
    title = "[{{ repo }}] {{ count }} commit(s) to {{ branch }}"
    body  = "{{ author }}: {{ commit_summary }}"
  }
}
```

## Configuration Directives

| Directive     | Type   | Required | Description                                                                                                                                                                                      |
|---------------|--------|----------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `source`      | string | Yes      | The integration source identifier (e.g., `threadbare`, `glassboard`).                                                                                                                            |
| `cipher`      | string | No       | Authentication mode: `hmac-sha256`, `bearer`, `ip-allowlist`, or `none`.                                                                                                                         |
| `destination` | string | Yes      | Delivery target in `protocol://topic` format.                                                                                                                                                    |
| `transform`   | block  | No       | <Terminology title="Envoy's payload transformation pipeline normalizing messages" to="/docs/terminology#parcel">Parcel</Terminology> transformation rules for the payload.                       |
| `retry`       | block  | No       | <Terminology title="Envoy's guaranteed-delivery engine with retry backoff" to="/docs/terminology#courier">Courier</Terminology> retry policy. Defaults to exponential backoff with 3 attempts.   |
| `filter`      | block  | No       | Conditional <Terminology title="Single declared pipeline from a source to destinations" to="/docs/terminology#relay">relay</Terminology> — only process messages matching the filter expression. |
| `fanout`      | list   | No       | Deliver to multiple destinations from a single source.                                                                                                                                           |

## Transform Block

The `transform` block defines how <Terminology title="Envoy's payload transformation pipeline normalizing messages" to="/docs/terminology#parcel">Parcel</Terminology> rewrites the payload. Fields use Mustache-style template syntax with access to the source payload.

```text title="Transform directives"
transform {
  title    = "[{{ severity }}] {{ alertname }}"
  body     = "{{ instance }} — {{ message }}"
  priority = severity_to_priority(severity)
  tags     = ["{{ severity_emoji }}"]
  actions  = [
    { label = "View Dashboard", url = "{{ dashboard_url }}" }
  ]
}
```

| Field      | Type         | Description                                                  |
|------------|--------------|--------------------------------------------------------------|
| `title`    | template     | Notification title. Supports template variables.             |
| `body`     | template     | Notification body. Supports template variables and newlines. |
| `priority` | number/fn    | Priority level (1-5) or a mapping function.                  |
| `tags`     | list         | Tag identifiers attached to the notification.                |
| `actions`  | list of maps | Interactive actions (view links, dismiss buttons).           |

## Retry Block

The `retry` block configures <Terminology title="Envoy's guaranteed-delivery engine with retry backoff" to="/docs/terminology#courier">Courier</Terminology>'s delivery guarantee behavior.

```text title="Retry directives"
retry {
  strategy   = "exponential"
  max        = 5
  backoff    = "1s, 5s, 30s, 2m, 10m"
  jitter     = 0.25
  dead_letter {
    enabled    = true
    retention  = "30d"
    escalation = "dispatch://fallback-channel"
  }
}
```

| Field         | Type   | Default       | Description                                                                                                                                                                            |
|---------------|--------|---------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `strategy`    | string | `exponential` | Retry strategy: `exponential`, `fixed`, or `immediate`.                                                                                                                                |
| `max`         | number | `3`           | Maximum retry attempts before <Terminology title="Terminal state after Courier's retries are exhausted" to="/docs/terminology#dead-letter">dead-letter</Terminology>.                  |
| `backoff`     | string | `1s, 4s, 16s` | Comma-separated delay schedule for each attempt.                                                                                                                                       |
| `jitter`      | float  | `0.25`        | Randomization range as a fraction of the current delay.                                                                                                                                |
| `dead_letter` | block  | enabled       | <Terminology title="Terminal state after Courier's retries are exhausted" to="/docs/terminology#dead-letter">Dead-letter</Terminology> queue configuration for undeliverable messages. |

## Filter Block

The `filter` block adds conditional <Terminology title="Single declared pipeline from a source to destinations" to="/docs/terminology#relay">relay</Terminology> logic. Only messages matching the filter expression are processed. All others are silently dropped.

```text title="Filter example"
relay "critical-alerts-only" {
  source = "glassboard"
  // highlight-start
  filter {
    severity = "critical"
  }
  // highlight-end
  destination = "canary://oncall-urgent"
}
```

## Multiple Relays

A single <Terminology title="Config file declaring every relay Envoy runs" to="/docs/terminology#relay-manifest-grain">manifest</Terminology> can declare as many <Terminology title="Single declared pipeline from a source to destinations" to="/docs/terminology#relay">relays</Terminology> as needed. <Terminology title="Protocol translator and relay engine between systems" to="/docs/terminology#envoy">Envoy</Terminology> loads all of them at startup and routes incoming messages to the first matching <Terminology title="Single declared pipeline from a source to destinations" to="/docs/terminology#relay">relay</Terminology>.

```text title="Multi-relay manifest"
relay "critical-glassboard"  { source = "glassboard", filter { severity = "critical" }, destination = "canary://oncall-urgent" }
relay "standard-glassboard"  { source = "glassboard", destination = "canary://infra-alerts" }
relay "threadbare-pushes"    { source = "threadbare", destination = "canary://ci-builds" }
relay "canary-heartbeats"    { source = "canary", destination = "canary://monitoring" }
```

:::warning Relay Ordering
<Terminology title="Single declared pipeline from a source to destinations" to="/docs/terminology#relay">Relays</Terminology> are evaluated in declaration order. If two <Terminology title="Single declared pipeline from a source to destinations" to="/docs/terminology#relay">relays</Terminology> match the same source, the first one wins. Place more specific <Terminology title="Single declared pipeline from a source to destinations" to="/docs/terminology#relay">relays</Terminology> (with filters) before general catch-all <Terminology title="Single declared pipeline from a source to destinations" to="/docs/terminology#relay">relays</Terminology>.
:::

## Validation

Validate the <Terminology title="Config file declaring every relay Envoy runs" to="/docs/terminology#relay-manifest-grain">manifest</Terminology> before starting the <Terminology title="Single declared pipeline from a source to destinations" to="/docs/terminology#relay">relay</Terminology>:

```bash title="Validate configuration"
envoy validate --config relay.grain
```

```text title="Validation output"
[validate] Loading relay.grain
[validate] Relay "glassboard-to-canary" ... OK
[validate] Relay "threadbare-to-canary" ... OK
[validate] 2 relays configured, 0 errors
[validate] Configuration is valid.
```
