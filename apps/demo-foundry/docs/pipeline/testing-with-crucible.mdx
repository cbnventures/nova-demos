# Testing with Crucible

<Terminology title="Generates test scaffolds from exported type signatures" to="/docs/terminology#crucible">Crucible</Terminology> generates test scaffolds from your type signatures. If you wrote the types, you already described the test contract.

<Terminology title="Generates test scaffolds from exported type signatures" to="/docs/terminology#crucible">Crucible</Terminology> reads the contract and writes the boilerplate.

## How It Works

<Terminology title="Generates test scaffolds from exported type signatures" to="/docs/terminology#crucible">Crucible</Terminology> scans every exported type signature in your <Terminology title="Foundry project declared in a .grain manifest" to="/docs/terminology#workspace">workspace</Terminology> packages. For each exported function, it generates a test file with:

- An assertion template matching the function signature.
- Fixture data derived from the parameter types.
- A snapshot test that captures the output shape.

```alloy title="src/utils/format.al — source"
export function formatDate(timestamp: Numeric): Text {
  return Temporal.format(timestamp, "YYYY-MM-DD")
}

export function formatCurrency(amount: Numeric, locale: Text): Text {
  return Intl.currency(amount, locale)
}
```

From these two exports, <Terminology title="Generates test scaffolds from exported type signatures" to="/docs/terminology#crucible">Crucible</Terminology> generates:

```alloy title="tests/format.assay.al — generated scaffold"
import { formatDate, formatCurrency } from "@my-app/core/utils/format"

// highlight-start
describe("formatDate", () => {
  it("returns Text for a valid Numeric input", () => {
    const result: Text = formatDate(1714780800)
    expect(result).toMatchSnapshot()
  })
})
// highlight-end

describe("formatCurrency", () => {
  it("returns Text for valid Numeric and Text inputs", () => {
    const result: Text = formatCurrency(49.99, "en-US")
    expect(result).toMatchSnapshot()
  })
})
```

The assertion templates use snapshot testing by default. The first run captures the output.

Subsequent runs verify it has not changed.

:::tip
Override any generated test by editing the file directly. <Terminology title="Generates test scaffolds from exported type signatures" to="/docs/terminology#crucible">Crucible</Terminology> respects manual changes — it only regenerates tests for functions that have no existing test file.

Set `crucible = manual` in your manifest to prevent all regeneration after the first scaffold.
:::

## Watch Mode

<Terminology title="Generates test scaffolds from exported type signatures" to="/docs/terminology#crucible">Crucible</Terminology> can watch for file changes and re-run affected tests:

```bash title="Watch for changes"
foundry crucible watch
```

In watch mode, <Terminology title="Generates test scaffolds from exported type signatures" to="/docs/terminology#crucible">Crucible</Terminology> monitors the <Terminology title="Resolves the dependency graph with query tools" to="/docs/terminology#tongs">Tongs</Terminology> dependency graph. When a source file changes, it re-runs tests for that file and all downstream dependents.

A change in `core` triggers tests in `core`, `api`, and `web`.

## Snapshot Testing

<Terminology title="Generates test scaffolds from exported type signatures" to="/docs/terminology#crucible">Crucible</Terminology>'s snapshot tests capture the output shape of a function. When the output changes, the test fails with a diff showing what changed.

```text title="Snapshot failure output"
  ✗ formatDate — snapshot mismatch

  Expected:
    "2025-05-04"

  Received:
    "2025/05/04"

  Update snapshot? Run: foundry crucible run --update-snapshots
```

:::info
Snapshot files are stored in a `__snapshots__` directory next to each test file. They are plain text and should be committed to version control.

Reviewing snapshot diffs during code review catches unintended output changes.
:::

## Fixture Generation

For functions with complex input types, <Terminology title="Generates test scaffolds from exported type signatures" to="/docs/terminology#crucible">Crucible</Terminology> generates fixture data automatically:

```alloy title="src/services/order.al — source"
export interface OrderRequest {
  customerId: Text
  items: List<OrderItem>
  shipping: ShippingMethod
}

export function processOrder(request: OrderRequest): OrderResult {
  // ...
}
```

```alloy title="tests/order.assay.al — generated with fixtures"
import { processOrder } from "@my-app/api/services/order"

const fixture: OrderRequest = {
  customerId: "cust_001",
  items: [{ sku: "item_001", quantity: 1, price: 29.99 }],
  shipping: ShippingMethod.Standard,
}

describe("processOrder", () => {
  it("returns OrderResult for a valid OrderRequest", () => {
    const result: OrderResult = processOrder(fixture)
    expect(result).toMatchSnapshot()
  })
})
```

<Terminology title="Generates test scaffolds from exported type signatures" to="/docs/terminology#crucible">Crucible</Terminology> infers sensible default values for each field type — strings get identifiers, numbers get realistic values, enums get their first variant.

## Configuration

<Terminology title="Generates test scaffolds from exported type signatures" to="/docs/terminology#crucible">Crucible</Terminology> respects the `crucible` directive in your manifest:

| Value    | Behavior                                                                                                                                                                                        |
|----------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `auto`   | Regenerates scaffolds on every <Terminology title="Running foundry ignite to generate workspace artifacts" to="/docs/terminology#forge--ignite">forge</Terminology> for new or changed exports. |
| `manual` | Generates once on first <Terminology title="Running foundry ignite to generate workspace artifacts" to="/docs/terminology#forge--ignite">forge</Terminology>. Never overwrites.                 |
| `off`    | No test scaffolding. You manage tests entirely.                                                                                                                                                 |
